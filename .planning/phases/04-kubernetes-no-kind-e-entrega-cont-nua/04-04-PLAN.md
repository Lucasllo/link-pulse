## Phase Goal

> Goal da ROADMAP (literal; ainda não está no formato de user story): Um avaliador roda `make k8s` e obtém o mesmo encurtador observável num cluster kind (Helm, Traefik, kube-prometheus-stack), enquanto o CI publica uma imagem escaneada no GHCR e comprova o deploy com smoke test.

Este plano entrega a metade "CI" do goal: critérios 4 (GHCR com Trivy e SBOM, nome minúsculo, pacote público) e 5 (job de verificação que sobe kind, faz deploy e passa no smoke) da ROADMAP.

<objective>
Estender o `.github/workflows/ci.yml` com três jobs: `image` (build + Trivy + SBOM, CI-03), `k8s-smoke` (kind + os scripts do avaliador com a imagem do commit, CI-04) e `publish` (só na main: push da imagem testada no GHCR com attestations, CI-02). Depois, o push da main e a mudança única de visibilidade do pacote, que só o usuário pode fazer, e a prova pública: pull anônimo e `gh attestation verify`.

Purpose: o avaliador encontra no GitHub uma imagem pública, escaneada, com SBOM e provenance verificáveis, e cada push prova o deploy no Kubernetes com o mesmo `make k8s` que ele roda.
Output: `ci.yml` com `image`, `k8s-smoke` e `publish`; README com a seção do pipeline; pacote `ghcr.io/lucasllo/link-pulse` público.
</objective>

Decisões travadas implementadas aqui: **D-11** (o smoke do CI é o `smoke.sh`, com UA de navegador), **D-12** (actions por SHA, inclusive o `aquasecurity/trivy-action`; versões conferidas pela pesquisa e pelo `git ls-remote` no planejamento).

Discricionariedade registrada (Claude's Discretion "Imagem no cluster" e "Pipeline GHCR/Trivy/SBOM"):
- **O smoke bloqueia a publicação** (Open Question 1 resolvida): `publish` depende de `build-test`, `image` e `k8s-smoke`, e empurra exatamente o tar que passou no Trivy e no smoke. O rebuild no publish foi rejeitado: o digest publicado não seria o testado.
- **Imagem no CI:** o `k8s-smoke` recebe a imagem do commit como artifact do `image` (`docker load`) e roda o mesmo `bash deploy/kind/up.sh` do avaliador, sem make (o `make k8s` rebuildaria).
- **Trivy:** falha só em CRITICAL com correção disponível (`ignore-unfixed`), scanners default (vuln e secret); trivy-action v0.36.0 com `version: v0.76.0` (o default interno da action é mais antigo). SARIF na aba Security fica de fora (Open Question 5: exigiria `security-events: write`, e PR de fork não recebe token de escrita).
- **SBOM:** CycloneDX gerado pelo próprio Trivy (sem action de terceiro a mais), como artifact em todo run e como attestation (`actions/attest` com `sbom-path`) no publish; provenance SLSA pelo mesmo `actions/attest` (o `attest-sbom` está em depreciação).
- **Tags:** `docker/metadata-action` com `type=sha` (`sha-{sha7}`) e `latest` na branch padrão; a action minusculiza `Lucasllo/link-pulse` (Pitfall 14).
- **Visibilidade:** o pacote nasce privado e a troca para público é manual e irreversível; a decisão "pacote público" já está travada no critério 4 da ROADMAP, então não há checkpoint de decisão, só o passo humano.

Fatos da pesquisa que mudam o desenho:
- `cancel-in-progress: true` em todo ref cancelaria um publish no meio de dois pushes seguidos na main (Pitfall 17).
- O post step do `helm/kind-action` com `install_only` falha o job sem `ignore_failed_clean: true` (Pitfall 18).
- O runner traz Helm 3.22: o `azure/setup-helm` fixa o v4.3.1 que o `up.sh` exige.
- O cache `type=gha` guarda as camadas, não o `--mount=type=cache` do `~/.m2` do Dockerfile: o build do CI baixa as dependências Maven a cada run (aceito; registrar o tempo no SUMMARY).
